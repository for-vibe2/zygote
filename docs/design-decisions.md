# Дизайн-решения компилятора Zygote

## Зачем писать компилятор на ассемблере?

### Образовательные цели
- Глубокое понимание низкоуровневых операций
- Изучение System V ABI напрямую
- Понимание управления памятью без абстракций
- Практика работы с регистрами и стеком

### Технические преимущества
- Полный контроль над генерируемым кодом
- Минимальные зависимости (только as/ld)
- Компактный исполняемый файл
- Прямое изучение архитектуры процессора

## Выбор AT&T синтаксиса

### Причины
- Стандарт для GNU Assembler (GAS)
- Совместимость с GCC inline assembly
- Широкая поддержка в Linux

### Особенности AT&T vs Intel
```assembly
# AT&T синтаксис
movq $42, %rax        # источник -> назначение
addq %rbx, %rax       # добавить rbx к rax

# Intel синтаксис
mov rax, 42           # назначение <- источник
add rax, rbx          # добавить rbx к rax
```

## Архитектурные решения

### 1. Многопроходная архитектура

**Выбор:** Отдельные фазы (lexer -> parser -> codegen)

**Альтернативы:**
- Однопроходный компилятор
- JIT компиляция

**Обоснование:**
- Четкое разделение ответственности
- Легче отлаживать и расширять
- Классический подход, хорошо документирован
- Упрощенная обработка ошибок

### 2. Рекурсивный спуск для парсинга

**Выбор:** Recursive descent parser

**Альтернативы:**
- Table-driven parser (LR, LALR)
- Parser generator (Yacc/Bison)

**Обоснование:**
- Простая реализация на ассемблере
- Прямое соответствие грамматике
- Хорошие сообщения об ошибках
- Легко понять и модифицировать

### 3. Статическое управление памятью

**Выбор:** Предварительно выделенные буферы фиксированного размера

**Альтернативы:**
- Динамическая аллокация (malloc/free)
- Сборщик мусора

**Обоснование:**
- Избегаем сложности malloc/free на ассемблере
- Предсказуемое использование памяти
- Проще отладка
- Достаточно для образовательных целей

**Ограничения:**
```assembly
input_buffer:  .space 4096   # Макс размер входного файла
ast_heap:      .space 8192   # Макс размер AST
output_buffer: .space 8192   # Макс размер выходного кода
```

### 4. Простое AST представление

**Выбор:** Линейная структура узлов с указателями

```assembly
# Структура узла (40 байт)
.quad type        # +0:  Тип узла
.quad value_ptr   # +8:  Указатель на значение
.quad left        # +16: Левый потомок
.quad right       # +24: Правый потомок
.quad next        # +32: Следующий сиблинг
```

**Обоснование:**
- Простая навигация по дереву
- Легко выделять из линейной кучи
- Поддержка списков через next

### 5. Минимальное подмножество C

**Выбор:** Только int, базовые операторы, простые функции

**Что включено:**
- Тип int
- Объявление переменных
- Арифметические операции
- Оператор return
- Функция main

**Что пока не включено:**
- Другие типы (float, char, etc.)
- Массивы и указатели
- Структуры
- Функции с параметрами
- Препроцессор

**Обоснование:**
- Фокус на ядре компилятора
- Управляемая сложность
- Легче тестировать
- Достаточно для демонстрации принципов

## Регистровое распределение

### Текущий подход: Naive allocation

**Стратегия:**
- Используем %rax для всех вычислений
- %rbx для временных значений
- Стек для сохранения промежуточных результатов

**Пример:**
```assembly
# a + b + c
movq a, %rax      # Загрузить a
pushq %rax        # Сохранить
movq b, %rax      # Загрузить b
popq %rbx         # Восстановить a
addq %rbx, %rax   # a + b
pushq %rax        # Сохранить
movq c, %rax      # Загрузить c
popq %rbx         # Восстановить (a+b)
addq %rbx, %rax   # (a+b) + c
```

**Проблемы:**
- Неэффективное использование регистров
- Много операций со стеком

**Будущее:** Graph coloring или linear scan

## Генерация кода

### Текущий подход: Template-based

**Стратегия:**
- Предопределенные шаблоны для каждой конструкции
- Прямая подстановка значений
- Нет оптимизаций

**Преимущества:**
- Простая реализация
- Предсказуемый результат
- Легко отлаживать

**Недостатки:**
- Неоптимальный код
- Много избыточных инструкций

## Обработка ошибок

### Текущая стратегия

**Фазы:**
1. Лексер: игнорирует неизвестные символы
2. Парсер: возвращает NULL при ошибке
3. Кодген: проверяет валидность узлов

**Сообщения:**
- Минимальная информация
- Без указания позиции в файле

### Планируемые улучшения

## Ограничения и trade-offs

### 1. Размеры буферов

**Ограничение:** Фиксированный размер 4KB для входного файла

**Trade-off:**
- ✅ Простота реализации
- ✅ Нет malloc/free
- ❌ Ограничение на размер программы
- ❌ Неэффективное использование памяти

**Решение:** Для продакшена нужна динамическая аллокация

### 2. Только функция main

**Ограничение:** Поддержка только одной функции

**Trade-off:**
- ✅ Упрощенная кодогенерация
- ✅ Нет таблицы символов для функций
- ❌ Не полноценный C
- ❌ Нет модульности

**Решение:** Добавить таблицу функций и поддержку вызовов

### 3. Отсутствие типов

**Ограничение:** Только int тип

**Trade-off:**
- ✅ Нет проверки типов
- ✅ Простая кодогенерация
- ❌ Нет type safety
- ❌ Ограниченная выразительность

**Решение:** Добавить систему типов

### 4. Нет оптимизаций

**Ограничение:** Генерируется неоптимизированный код

**Trade-off:**
- ✅ Простая реализация
- ✅ Предсказуемый вывод
- ❌ Медленный код
- ❌ Большой размер

**Решение:** Добавить проходы оптимизации

## Масштабируемость

### Легко расширить

1. **Новые ключевые слова**
   - Добавить в список keywords
   - Обновить парсер

2. **Новые операторы**
   - Добавить в лексер
   - Добавить в парсер
   - Добавить шаблон в кодген

3. **Простые типы**
   - Добавить проверку типов
   - Обновить размеры в кодгене

### Сложно расширить

1. **Указатели**
   - Требует адресной арифметики
   - Усложняет типовую систему
   - Нужна работа с памятью

2. **Массивы**
   - Вычисление индексов
   - Проверка границ
   - Многомерные массивы

3. **Структуры**
   - Вычисление смещений
   - Выравнивание данных
   - Копирование структур

## Альтернативные подходы

### 1. Виртуальная машина

**Вместо:** Прямая генерация x86_64

**Подход:** Генерация байткода для VM

**Плюсы:**
- Проще генерация кода
- Портируемость
- Легче добавлять фичи

**Минусы:**
- Нужна реализация VM
- Медленнее native кода
- Не изучаем реальную архитектуру

### 2. LLVM IR

**Вместо:** Собственный кодген

**Подход:** Генерация LLVM IR

**Плюсы:**
- Бесплатные оптимизации
- Множество целевых архитектур
- Production-ready

**Минусы:**
- Сложнее понять процесс
- Зависимость от LLVM
- Не пишем кодген сами

### 3. Интерпретатор

**Вместо:** Компиляция

**Подход:** Прямое исполнение AST

**Плюсы:**
- Проще реализация
- Динамические возможности
- Нет фазы кодгенерации

**Минусы:**
- Медленнее
- Не изучаем генерацию кода
- Нет оптимизаций

## Уроки и выводы

### Что получилось хорошо

1. **Чистая архитектура** - четкое разделение фаз
2. **Простота** - легко понять каждый компонент
3. **Образовательность** - каждая строка учит чему-то

### Что можно улучшить

1. **Обработка ошибок** - нужны лучшие сообщения
2. **Масштабируемость** - фиксированные буферы ограничивают
3. **Производительность** - наивная кодогенерация неэффективна

### Ключевые инсайты

1. Компилятор - это преобразование представлений
2. Ассемблер дает полный контроль, но требует внимания к деталям
3. Простые решения часто достаточны для начала
4. Инкрементальный подход позволяет построить рабочий компилятор

## Заключение

Zygote демонстрирует, что можно построить функциональный компилятор на чистом ассемблере. Проект показывает фундаментальные принципы компиляции и дает глубокое понимание работы компьютера на низком уровне.

Хотя реальные компиляторы используют более сложные техники, базовые принципы остаются теми же.
